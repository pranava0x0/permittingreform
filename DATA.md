## Data handling

- **Append-only.** Append rather than overwrite; dedup by unique key.
- **Append-only history is a child table, not an overwrite.** Keep the latest value on the parent for the hot path, and append one immutable row per observation to a child table for the curve. Write child rows by explicit foreign key, not `parent.children.append()`; the relationship append lazy-loads the entire ever-growing collection on every write. Derive display series (sparklines) at read time with one windowed query for the whole page, never a query-per-row.
- **Source attribution.** Every record carries its origin (source URL, connector, capture date) so any value traces back.
- **Defensive optional fields.** Null-check before rendering or processing.
- **Null renders as an explicit placeholder** ("N/A", "—"). Never a blank element.
- **Empty ≠ broken.** A legitimately empty result (clean audit, no matches) is valid. Render an explicit "none" state. An *extraction failure* is a bug. Log it and track coverage in `issues.md`. A silent `0` conflating the two reads as "covered everything" when it didn't. Concretely: don't `return []` for both a fetch failure and a real empty parse. An adapter that folds "source was down" into "source had nothing" makes a broken feed indistinguishable from a clean sweep; log the two paths differently and surface a per-source fetched/parsed count.
- **Generated output commits with its source.** Seed + baked JSON, or rules + derived `llms.txt`, move together (a bisect must never land on an inconsistent state); assert the match with a test.
- **Resolve conflicts in data/generated files by union, not by hand** (2026-07). When two branches both edited a large JSON/CSV data file, merge programmatically by unique key — union the record arrays, reconcile only the overlapping ids (prefer the newer/more-accurate curation), then re-run the build to regenerate derived outputs (`docs/data/*`). Hand-editing conflict markers inside a big data array or a generated file is error-prone; key-union + rebuild is deterministic and reviewable. (A build step that stamps `generated_at`/today means the derived files *always* show a diff even when source content is unchanged — expected, not a regression.)
- **Capture dates over "current" framing.** Record `captured_at` and surface "as of YYYY-MM-DD"; record `archived_via` when a value came from a secondary/archived source.
- **Don't re-stamp `captured_at` on a re-parse.** A run that regenerates output from unchanged cached bytes preserves the original capture date. Load prior dates before processing and only re-stamp reissued (byte-different) sources. Stamping everything to today churns the audit trail and misrepresents provenance.
- **Keep bounded values, don't drop them.** A bare `\d+%` regex silently discards real rows like `>99%` / `<1%`; parse `[<>~]?(\d+)%`, keep the number, and carry the bound as metadata. Dropping unparseable-but-real values is a silent coverage gap, not a clean filter.
- **Preserve raw values when cleaning.** Normalizing a name/date/location/category? Keep the original in a parallel `*_raw` field. Cleaning is lossy, and raw is the only way to debug a bad transform or re-derive under new rules.
- **Cap by content, not count.** Trimming an append-only collection to a fixed count silently drops the oldest valid records. Bound by a content predicate (date window), store everything, limit *display* in the UI (top-N + "show all"). Log a threshold warning; never let the data layer enforce the cap. This applies to derived single-file build artifacts too: if one hits a size limit, filter what that *one artifact* renders (e.g. by a status/date predicate), never delete or exclude the underlying source records.
- **A duplicate "freshness" field drifts silently unless one is derived from the other.** A top-level "last updated" stamp that isn't touched by the automation that updates the real underlying data (only a sub-file gets bumped) goes stale for days before anyone notices. Derive the duplicate at build time, or test that both dates match.
- **Quality/confidence is its own field.** Keep geocoding confidence, match certainty, modeled-vs-observed separate from the value. A high-severity record with a low-confidence location differs from a clean one, and conflating them hides the gap.
- **Separate facts, estimates, and judgments** into distinct labeled lanes. A tool may have a view but mustn't manufacture certainty. Show the data and mechanism behind a recommendation, never a black-box score.
- **Publication date ≠ capture date.** Store the source's own publish date separately from `captured_at`; show publish when present, else capture. Don't fabricate a date for an undated source. Leave it null.
- **Absence of a judgment is meaningful.** An empty curator field (status, verdict) means "not yet assessed," not a default. Don't auto-fill or add a catch-all "unknown". Leave it off so the record reads as it did before the field existed.
- **Verify external state before trusting memory.** Registry lists, rosters, and configurations that external services publish (API endpoints, MCO enrollment lists, state agency site structures) can change month-to-month without announcement. Never shortcut with "I verified this in a prior session"—re-check before baking into a guide. Why: an MCO exits a state, a vendor changes the URL scheme, or an API deprecates a route; using stale state ships wrong data silently and requires a future retraction. How to apply: when a data source claims "this applies to X entities" or "this service serves Y," spot-check a sample against current live data before generalizing.
- **Contested → show both sides.** When a third party documents a shortfall the subject disputes, tag it "contested" and surface both sources. Don't pick a winner. Reserve the strongest adverse status for ≥ 2 independent sources or a citable regulator/court finding.
- **Rates need denominators.** Raw counts mislead across groups of different size. Rank by a rate against an exposure measure (volume, population, length); label any raw-count ranking a triage heuristic, not a verdict.
- **Keep incompatible frames labeled and never summed.** Two totals in different frames (general fund vs all funds, gross vs net, nominal vs real, operating vs total) describe different things; presenting them without the frame label, or summing/differencing across them, manufactures a false number. Beware hierarchical rows that already contain their children (a department total that also lists each office beneath it): summing the flat list double-counts, so use the source's own subtotal, not your sum. When only one frame is verifiable, show it and say which, rather than fabricating the other from a mismatched source.
- **Don't rank incomparable series on one scale; lane them, then normalize within the lane.** When a metric means different things across groups (a search-traffic estimate vs. a "present in feed" flag), a single global sort silently implies a comparison that doesn't exist. Group by the incomparable dimension, rank within each, and expose a within-group normalized value (min-max over that group's population, computed at read time) for any bar/meter. Carry the unit so the record self-describes.
- **A content-safety filter should over-block, not precision-match.** For a family-safe/NSFW/moderation gate, a false negative (bad content slips through) is worse than a false positive (an innocent item dropped), so prefer a conservative substring match over word-boundary matching (`\bporn\b` misses "Pornhub"). Tune the blocklist to kill the worst false positives instead, count what it drops each run so an over-broad rule is auditable, and treat the keyword pass as a cheap first gate under a real classifier, not the final word.
- **Don't re-identify anonymized data.** Combined records can re-identify individuals. Aggregate small counts before surfacing; don't publish a precise individual narrative unless already public and necessary.
- **AI-synthesized values are provisional.** LLM aggregations from secondary round-ups aren't citation-grade. Audit each against a primary source, stamp `verified_at` + a per-row source; don't ship them as fact.
- **A 200 + a real file is not proof the source backs the claim.** A guessed identifier (docket / order / case number) can resolve to a real but *unrelated* document. Verify the *content* matches (page-1 caption: entity, date, identifier), not just that the URL loads. Prefer self-proving artifacts (a downloaded PDF with `page_count > 0`) over a metadata-only "verified" flag; the un-fetched escape hatch is the fabrication vector. Set a "suspiciously small" warning threshold above the minimum-size floor: a blank placeholder PDF can pass a naive size-floor check. A citation that quotes correctly can still cite the wrong paragraph/section (e.g. a concurrence mistaken for the majority holding) — re-check the identifier against the actual document, not just the substance.
- **LLM "gap filling" can fabricate whole records that pass schema validation** — invented IDs, guessed URLs, future `captured_at` dates, self-incriminating "pending verification" language. Any manual/deferred-verification escape hatch (built for blocked sources) is also the exact vector fabricated data slips through unchecked; guard it against fabrication markers, don't let it skip validation silently. Before trusting an abandoned/uncommitted diff left by a prior crashed run, inspect it — it can carry the same fabricated content into the next session.
- **A real identifier attached to an invented claim is the fabrication a schema, a 200 and a spot-check all miss (2026-09-24).** In one tracker, an earlier LLM "enhancement" pass had added a batch of nine state moratorium records. Five were fabricated: Massachusetts, Vermont and Idaho each carried a real bill number (a veterans bill, an equal-pay bill, a county-commissioner bill) attached to a data center moratorium that never existed; Washington and Oklahoma had the same defect; Maine's was vetoed, not enacted; Denver had the wrong sponsors, vote and source. The base rate of a batch (5 of 9) is the finding, and it came from opening each identifier's own page and comparing its title to the claim. Nineteen more records in the same file cited only a homepage. A homepage cannot contradict anything, so the batch passed. **Treat a record whose only source is a homepage as unverified, count them, and audit an LLM-written batch as a batch, not one row at a time.**
- **A pair of numbers from one report can be internally consistent and still describe a different thing (2026-09-24).** A pitch deck quoted "$22,000 per kW and $325 per MWh" for a heat-pipe microreactor. Both figures trace to the same national-laboratory report and the same reference design, a generic 20 MWt liquid-metal reactor, not the heat-pipe design the deck was about; the same deck's slide 2 already said $980 per MWh for the first heat-pipe unit and $450 mass-produced. When a figure is attached to a named subject, check that the source's subject is that archetype, then grep the same artifact for the same quantity elsewhere: two prices for one thing in one deck is a defect a reader finds in a minute.
- **A ranking that sums distances ranks by whatever is near zero everywhere (2026-09-24).** A siting tab ranked 17,256 brownfields; **0 of the top 150 had confirmed land**, because every scored component was a distance to infrastructure and urban parcels score near zero on all of them. Detroit and Philadelphia lots scored 94-96. The tab answered "which brownfield sits in the densest infrastructure", not "where could a refinery go". Before shipping a ranked list, read the top 20 against the question the tab asks (is it available, is it big enough), and make a required attribute a gate, not a term in the sum. The user's four questions ("are these suitable", "why are the scores so high", "are these plots even available", "outside Michigan and Maine?") were each answerable from the data in one query.
- **Three homepage stats on one site were wrong in three different ways in one day (2026-09-24).** A hero field (`reactors_critical_2026`) was hand-set to 3 and never updated; the real count was 5. A coverage counter treated any non-null value as "have", so two rows reading "N/A; DOE-authorized test reactors" produced "2/16 have a utility filing". A "17 vendor milestones hit in 2026" tile summed a criticality event, a hire, a funding close and a base selection: the arithmetic was right and the number meant nothing, so the tile was removed. Derive a stat from the rows, count N/A as its own state, and before showing a total ask what single unit it counts.
- **federalregister.gov serves scripted clients a "Request Access" page; govinfo.gov returns the same document's text.** `https://www.govinfo.gov/content/pkg/FR-YYYY-MM-DD/html/<doc-number>.htm` works with plain `curl`. Cite the federalregister.gov URL and verify against the govinfo copy. Likewise congress.gov answered a scripted fetch with HTTP 403 while govinfo's `BILLS-119s4668is` details page loaded. A 403 to `curl` is bot protection, not a dead link.
- **A live/dynamic source page is not a durable citation target.** It drifts, gets gated, or 403s later. Capture and link a fixed snapshot as primary; keep the live URL as secondary context.
- **Gate an extraction against the source's own declared total.** Many documents state their own count ("Audit staff identified N areas of noncompliance"). Accept a parsed list only if its length equals N (or within a tight band like 90–100%); otherwise fall back to metadata-only rather than emit a partial or garbled parse as if it were complete. A self-declared count is a free oracle: use it to reject wrong verbatim text instead of shipping it.
- **Survey the real distribution before hardcoding an allowlist.** An exact-match allowlist drops the long tail (casing/prefix variants). Check the actual value distribution first, and filter on a stable underlying type, not the human-entered label, when one exists.
- **Prove a bulk deletion is content-free before trusting it.** When purging crawler junk or off-theme rows, regenerate the derived output and diff it: if `findings.csv` (or the equivalent product surface) is *byte-identical* after removing the rows, they carried no signal and the purge is safe. A changed output means you dropped real data. Stop and review. Crawler seeds silently accumulate off-theme noise (URL-encoded filenames, unknown type, 0 content, `structured=false`); audit by structural signature, not by eyeballing.
- **Enforce a source-host allowlist in code.** When data must come from authoritative origins, make the loader *raise* on any off-origin URL (e.g. non-`.gov`). Don't trust reviewer vigilance. Test it over every committed seed. A legitimate source that doesn't conform to the general pattern (a state agency on `.org`, not `.gov`) gets a narrow, exact-domain exception — don't loosen the general rule to fit one case.
- **Bidirectional fields (who owes whom, credit/debit direction) must not hardcode one direction as always-true.** A settlement, refund, or close-out payment can flow either way depending on state; name tokens/fields by direction (`credit`/`debit`), not by a fixed role, or the value silently misattributes when the direction flips.
- **External-API IDs are often non-dense.** Gaps from deleted/orphaned records are normal — never assume `1..N` or that display position N is entity N (sort order is usually a derived stat, not ID order). Iterate the actual ID list, and key identity on the immutable ID, not a display name that can change mid-session.
- **Sentinel values from an external API** (`-1` for "none", `0` for "unset") **must map to an explicit display placeholder, the same way any null does** (see "Null renders as an explicit placeholder" above) — never concatenate the raw sentinel into a label. Store the sentinel as-is; only the display layer translates it.
- **Validate against a relative baseline, not a fixed absolute floor.** A floor tuned for typical values (e.g. "$20 minimum") lets an obviously-bad outlier through once the surrounding distribution moves (a $29 listing against a $300 median). Compare to a rolling measure (e.g. `< 0.2x median`) instead.
- **Vendor/deep-link URLs aren't interchangeable across destinations.** Normalize per the target vendor's own URL scheme; don't reuse a display label as a slug for a different vendor's link format, and omit the link entirely rather than guess when no confident match exists.
- **A generated/computed value must not contradict the authored content it sits beside**, and a worked numeric example should show the computed result and its direction, not just the formula — a formula alone doesn't verify the computation and doesn't teach.
- **An archival/rollup step that moves old rows into a summary table and deletes the originals breaks every downstream reader that still queries only the detailed table.** Any two-tier storage migration needs an audit pass across all readers, not just the writer that does the rollup.
- **A stale artifact predating a schema field addition can be silently backfilled with wrong defaults on read** (a validator fills defaults for missing fields even under a strict/`extra="forbid"` mode). Re-validate old artifacts explicitly after a schema change rather than trusting the loader's default-fill.
- **Before `.gitignore`-ing a derived artifact as "regenerable from committed data," verify that claim.** A file that depends on a gitignored upstream's internal structure (a PDF's bookmark/outline metadata, not just its text) isn't actually reproducible from what's committed — a re-run can't recreate it once the raw source is gone. Commit it instead of trusting a comment that says it's derivable.

- **Derived metadata must key off the artifact, not its subject.** A page's `dateModified` (and sitemap `<lastmod>`) was computed from the newest date among the *things the page describes*, so a day spent rewriting the page's own bio, prose and layout left it still claiming a date from three weeks earlier — and always would have, since editing a document never moves its subjects' dates. Ask what the field is a statement *about*: if it describes the document, derive it from the document (git's last-change date for that file, treating uncommitted edits as today, since the generator usually runs as part of the change it's describing). Take `max(subject, artifact)` when both are meaningful.

- **A source's heading routinely claims more than its body supports — quote the body.** A tracker rendered five commitments under a footnote promising they were "quoted verbatim"; the titles were, the descriptions were paraphrases, and two had drifted in the direction that flattered the subject. One restated the *section title* ("Paying Whether They Use the Power or Not") as though it were the commitment, when the body said only that the parties would negotiate rate structures. The other silently dropped a "whenever possible" hedge, turning a qualified promise into an unconditional one. Both read perfectly and neither was catchable by checking that the link resolved. If you claim verbatim, pin the strings in a test so re-tightening them into snappier copy is a deliberate edit; and if a layout needs them shorter, shorten the layout, not the quote.
- **A verbatim quote-lock proves the string exists on the page; it proves nothing about which quantity a paraphrased field attributes it to.** (2026-08-29, a research/citation dataset project) A benchmark record's `capacity` field said a $95.1M utility substation delivered "up to 500 MW" — a real, verbatim-quotable figure from the cited source, and the quote-verification gate passed it clean. But that 500 MW was the buyer's eventual *full-site* draw, quoted from the same article; the substation itself was 50 MW, stated two paragraphs later in the same piece. The citation gate checks that a quoted span exists in the cached bytes — it has no way to know the record's own numeric field pointed at the wrong sentence. Caught only by an adversarial review round that fetched the primary source and read past the first matching number. When a record's own summary/capacity/price field states a number, re-derive it from the full surrounding context of the quote, not just the sentence containing the quotable span.


## Error resilience

- **Never let one item crash the pipeline.** Wrap per-record processing; log and continue.
- **Log aggressively:** every request, parse, API call, cache hit/miss, filter decision.
- **Cache everything fetchable** so re-runs are fast and cheap.
- **Validate everything.** Invalid external responses → log and skip, never crash.
- **Track errors visibly** in `issues.md` or an errors array. Failures must surface.
- **Add a freshness canary for data that goes stale when an upstream stage advances.** When correctness depends on an external stage advancing (a bill enacts, a filing posts, a document reissues), a scheduled probe should diff the authoritative index against a committed snapshot and open an issue on drift, detection only, never auto-ingest. The staleness this catches is the kind nobody notices until the surface embarrasses itself (a site still calling an enacted budget "proposed"); the probe makes the next drift loud instead of quiet.
- **Checkpoint long jobs incrementally.** Save per unit, commit per N units / per partition, and log every failure to an append-only `ingest_log.jsonl` with a `retryable` flag. End the run with a one-line status report (`✓ N done · ✗ M failed (reason) · → resume at X`). A job that only reports success hides the items that silently fail every re-run. **Derive the denominator from the work list; never hardcode it beside the list it counts.** A puller whose summary line said `/21` printed `pulled 23/21` for an entire session and nobody flinched — the literal was written when the list held 21 ids and never moved again, so the one number that could have caught a *short* run had quietly stopped being a check at all. It survived the list growing to 23 and would have survived it growing to 26. A count that cannot be wrong in the safe direction cannot be right in the dangerous one: `TOTAL = sum(len(v) for v in WORK.values())`. Same disease as a duplicated freshness stamp, and the tell is identical — a number that disagrees with its own data and gets read as cosmetic.
- **Resume/backfill merges with on-disk output.** A `--missing-only` run must merge new records with existing *before* writing, or a capped partial run drops everything done earlier. Keep a progress manifest (per partition: `last_run`, `count`, `next_target`) so a new session resumes without re-deriving progress. Distinguish a closeable gap from a permanent source-side dead-end. Don't re-run enrichment for data upstream will never give; mark it a known structural gap.
- **Checkpoint long jobs to disk, not session memory.** Work directories (intermediate state, progress counters, checkpointed records) don't survive across agent sessions or restarts. Write to disk at every phase boundary so a killed or suspended job can resume from the last checkpoint; don't rely on in-memory state or log output to reconstruct progress. Why: a workflow rate-limit kill / session timeout / operator abort leaves in-memory work unrecoverable; on-disk state is portable and auditable. How to apply: end each loop cycle with `write_json("checkpoint.json", {last_id, count, next_target})` or append to a `.jsonl` log.
- **Re-run a nondeterministic stage on failed records only, never blind-rebuild a validated corpus.** OCR, some PDF text extractors, and LLM passes don't return identical output twice; a whole-corpus re-structure drifts already-good records (one blind re-run dropped a validated report from 12 findings to 1). Make any recovery/backfill pass *additive and gated*: run it only where the primary path produced nothing, so the diff touches only the recovered ids and validated records can't regress. Process pathological-size inputs individually: a batch pipeline OOM-kills on the largest item and silently loses the rest of the batch.
- **Verify files are really on disk before debugging a "code" bug.** Cloud-sync (iCloud / Dropbox / OneDrive) can leave dataless placeholders that read empty / NUL while the inode reports the right size, and `git status` calls them *clean* because it trusts its stat-cache and never reads the bytes. The symptoms masquerade as code bugs (`ERR_INVALID_PACKAGE_CONFIG`, every route 500s, multi-minute boots, `page 2.tsx` conflict-copies, a Python `PermissionError` on `os.getcwd()`). Fix: delete the file *then* `git checkout` (a plain checkout no-ops on a "clean" placeholder); better, move the repo out of the synced folder (or serve from `/tmp`, re-syncing source on every edit, if you can't move it).
- **Key file-backed caches on a signature, not a TTL.** For a cache fronting a local file, key on `(mtime_ns, size)` instead of a fixed `ttl=`; it busts the instant the file changes and serves indefinitely otherwise. A time-based TTL either serves stale data or churns needlessly.
- **Cache keys must be the caller's own stable identifier, never a volatile token.** Keying on a response-generated ID (changes every call) or on `id()` of a per-request connection object (a fresh object every request) silently gives 0% hit rate forever, with no error to notice it by.
- **A web-fetch tool's own "I can't read this" message isn't proof the source is unreadable — check what it already saved.** An AI-summarization fetch step can choke on a PDF ("corrupted or encoded... binary data") even on a small, well-formed file (confirmed on 135KB/313KB PDFs, not just huge ones); the tool result still names the local path where it saved the raw bytes before giving up on summarizing them. Read that path directly (native PDF support) before concluding the source needs a different fetch method or is unreachable.
- **Native parsers can silently succeed with a wrong value instead of throwing.** `new Date("March 29, 2026 TBD")` parses to midnight UTC rather than erroring, shifting a future event into the past in a US timezone. Validate parsed dates/numbers against a sanity range, don't trust "it didn't throw" as "it's correct." **Hand-rolled parsers have the same failure in regex form:** an unbounded day group `(\d{1,2})` matches the first two digits of a four-digit year, so "March 2025" becomes March 20th and the year gets guessed — anchor it with `\b` and sanity-check the result (2026-07-29).
- **A conditional write gated only on business-logic state (not rows-affected) can silently no-op.** An RLS policy or a permissions check can block an `UPDATE`/`DELETE` and return 0 rows with no exception; the app proceeds as if it succeeded. Check rows-affected for any write the app's correctness depends on.
- **A poll/wait loop must log each attempt and surface the last status or error in its timeout.** A `while not live: sleep()` that only checks the success case and raises a bare "never became ready" discards the cause: a permanently broken target (auth disabled, wrong URL) is indistinguishable from a slow one, and whoever's debugging is flying blind. Capture the last status/exception, log each iteration, fast-fail on a status that will never heal (401/403), and put the last status plus a body excerpt in the raised error.
- **A spend cap or rate guard must count on the column that signals the action, not a later terminal timestamp.** If an external id (a posted-tweet id) commits a step before the timestamp that marks success, counting the period's actions by that terminal timestamp silently omits any attempt that fired the side-effect then crashed before completing (its terminal timestamp is null), and the cap gets walked past. Count on the signal column itself, with a window that also catches fired-but-unfinished rows, and bias the estimate toward over-counting: a guard should fail closed.

- **`TimeoutError` is an `OSError`, not a `urllib.error.URLError` — a read timeout escapes `except URLError` and kills the whole run.** A personal CRM app's news sweep wrapped each person's fetch and converted only `HTTPError`/`URLError` into its own `FeedUnavailable`, which was the sole exception the per-person loop caught. One slow feed raised a bare `TimeoutError`, sailed past the handler, and took down the sweep — the digest printed nothing for any contact, which is exactly what the code's own comment promised could not happen (*"One person's failure never takes the run down"*). **A per-item resilience loop must catch the base class you actually mean (`Exception`, or `OSError` if you want to stay narrow), not an enumerated list of the failures you happened to think of.** Any comment asserting isolation is a test that should exist: inject a timeout into one item and assert the other items still produce output.
- **"Always drop the last line" is only correct for a *truncated* prefix — on a fully-read file it discards a real record.** A dev-tooling dashboard's log parser's `completeLines` unconditionally dropped the trailing line to avoid emitting a half-written one. For small files read in their entirety that silently threw away the **newest** record of every log — precisely where `custom-title` and the final prompt live, i.e. the rows most likely to be the ones you are reading the log for. The boundary rule has to be conditional on whether the chunk actually hit a read limit; if the read consumed the whole file, the last line is complete by definition. Tests caught this one only because they exercised a small file as well as a large one — parser coverage that uses only realistic-size inputs will not find it.

## Network ethics & rate limiting *(when fetching from external sources)*

- ≥ 1.5–2s between requests to one host. Informative `User-Agent`. 429 → exponential backoff from 10s.
- Cache all fetched content to disk; re-runs never re-download.
- Persistent block after retries → log to `issues.md` and skip, never crash.
- **Start small:** validate against a handful of pages before a full run.
- **Distinguish failure classes before retrying.** Fail fast, no retry, on TLS/cert errors and 401/403 (auth wall or WAF); reserve exponential backoff for transient errors (timeouts, connection resets, 429s). A generic retry-everything loop wastes cycles re-hitting a wall that will never open.
- **An advertised API limit can be silently wrong for a specific request shape.** A documented `maxRecordCount` may only hold below some other parameter (e.g. it 500s above 1,000 rows only when a geometry flag is also set). Discover the real limit empirically for your actual query, don't trust the docs alone.
- **A JS-rendered "data portal" that returns nothing to `curl`/`WebFetch` often has an underlying machine-readable endpoint (REST/RDB) hiding under the JS-only UI.** Look for it before concluding the data isn't scriptable. SaaS-hosted pages are the easiest case, because the vendor documents the API for everyone: five JS-rendered job boards across four vendors all resolved to two public JSON endpoints (`api.ashbyhq.com/posting-api/job-board/<org>`, `boards-api.greenhouse.io/v1/boards/<org>/jobs/<id>`), so 23 pages became one cached script and zero scraping. Identify the *vendor* from the URL shape first; the ID format usually gives it away.
- **When one API returns the same fact twice, assume the copies disagree, and know which one is authoritative.** A job board's structured `compensation` field and the salary range written in the posting body differed on three of five roles at one company ($300–390K vs. $350,000–$500,000): the body carries the legal pay-transparency obligation and is what a human sees, while the structured field was a stale tier. Quoting the convenient one would have understated by $110K. Cross-check both, prefer the one with authority (legal text, the rendered surface) over the one that's easy to parse, and record which you took and why.
- **Some consumer-facing sites (price-comparison aggregators, e-commerce) bot-block plain fetches/`WebFetch` outright, with no hidden API underneath.** Confirm there's no API first; if blocked, a live browser session is the only path in — and stamp the result with a captured-at date, since prices on these sites drift daily and the value is a snapshot, not a constant.
- **A plain fetch on a large government PDF can return binary/metadata with no readable page text even though the PDF is real and fetchable.** Same "looks dead but isn't" failure class as a bot-blocked page, different cause (parsing, not blocking). Try a dedicated PDF-reading tool on a large formulary/PDL/report before downgrading verification on the assumption the source is unreachable.
- **Prefer a source's structured API to scraping its PDFs, but verify the real endpoint and commit the raw response as evidence.** When an authority publishes both a document and a data service for the same numbers, ingest the service (reproducible, versioned, deep-linkable) and cite the document. Probe the service's own help/index for the actual endpoint rather than trusting a documented or guessed path. Cache the raw XML/JSON and commit it alongside the derived output (small text is the evidence), with a test that re-parses it so the repo self-verifies offline; preserve the fetch date across an offline re-parse instead of re-stamping it.

**2026-08-05**

- **Collection gets a script; judgement does not.** Anything mechanical and repeatable — validating source hosts, checking links, generating derived files, linting prose — belongs in a committed script with a named command, so the next session runs `npm run data:check` instead of re-deriving the method from scratch. Anything requiring a read — *does this page actually support this claim*, *is this the best available source* — stays a human or agent read, recorded next to the record it justifies. Automating the fetch is easy and automating the judgement is the thing an evidence product exists to avoid; keeping the boundary explicit is what stops the second from quietly becoming the first.

- **One URL attached to two facts in a research note propagates a mis-citation into the product.** A fact-pack bullet listed a groundbreaking *and* a licence acceptance under a single link. The link documented only the second. It reached the shipped page as the source for the first, drove a company's rank on the board, and survived three review rounds because it resolved, looked plausible, and sat on a national-lab domain. **One fact per source**: if a record's visible label makes two claims, cite the source carrying both or split the record. Auditing that shape across the dataset found four more.

- **A figure written into prose beside the data it describes goes stale silently, and will do it repeatedly.** The same band total drifted out of date **four separate times** in one session — in a README, in an implementation record twice, and in a UAT baseline whose "last run" date had been moved forward while its counts had not. Each fix was correct and each was overtaken by the next data change. Regenerating is better than editing, and a test that greps the prose for the current figures and fails on a mismatch is better than both; it is about six lines and it ends the whole class.

- **A mechanical bulk edit needs a section boundary, not just a pattern.** A script relabelling records matched on indentation depth and rewrote **nine curated records** in an unrelated array as collateral, because they happened to be indented the same way. Anchor the edit to the region it is allowed to touch (slice the file at a known marker, then edit only the tail), and diff the untouched region to prove it is untouched. Same family as never regex-renaming across a whole file: the pattern is not the scope.

- **A threshold that cannot span the real range of the data is worse than no threshold, because it fails as a false accusation.** Two in one session. A 5,000,000-acre sanity ceiling flagged `NORTHWEST MANEUVER AREA` (8.05M acres) as corrupt — WWII maneuver areas were training *regions*, and Tennessee's really is 4.26M, so any cap tight enough to catch garbage rejects real data. And a fixed 60-mile bounding box built to *evidence* a distance returned zero features for the sites 60–100 mi from their nearest feature, so the citation read as a refutation of the claim it supported. Derive the bound from the data's own range (the site cannot be larger than its state; the box must be sized from the distance it is proving), not from a round number that felt safe.

- **Do not delete data on a heuristic — flag it.** A rule dropping values that disagreed with the authoritative layer by more than 100× correctly caught an 11,014,908-acre figure for a site whose surveyed boundary is 1,357 acres. It also deleted a perfectly ordinary 153.7-acre value whose only sin was sitting against a 1.0-acre baseline: small denominators make ratios explode. Implausible-but-not-provably-wrong data stays, and stays reported. The same restraint applies to 118 coordinates that plot outside their own stated state — inventing a correction we have no source for is worse than publishing a flagged one.

- **An API can return its errors with HTTP 200.** Every ArcGIS FeatureServer does: a bad field name comes back `200 {"error": {...}}`, `raise_for_status()` sails past it, and `payload.get("features")` reads downstream as *"the source has no such record."* A validation script then reports its own bug as a data finding — which is worse than having no script. Check for the error key explicitly, and treat "source doesn't have it" as a conclusion that requires a successful response first.

- **A citation is only evidence if it resolves to the specific claim; otherwise it is decoration that rots.** Building per-field provenance for a dataset, two agency landing pages cited as sources had died quietly — one domain no longer resolved at all, another 301'd into a different tool and then bot-blocked. Both were replaced with point-in-polygon queries against the services the pipeline actually calls: same question, verifiable rather than merely reachable, and impossible to rot without the pipeline breaking too. Prefer a URL that returns *this record* over one that describes the dataset, and put a link checker on it — 488 links checked, four broken, all four found only because something fetched them.

- **A negative claim is evidenced by an empty result, so a link checker must be told which claims are negative.** "Not in an Opportunity Zone" is correctly proved by a containment query returning nothing. Without a per-row `expectsFeatures` flag, the checker reports every correct negative as a dead citation and buries the real failures in noise.

- **WebFetch on a PDF burns a call and returns binary; download it and parse locally.** Federal reports are PDFs. `curl -L` with a browser User-Agent (several agency hosts 403 a bare fetch) plus `pypdf` extracts 127 pages of text locally, greppable as many times as needed for the cost of one download — versus one fetch call per question. Check for `pypdf` before reaching for `pdftotext`, which is often not installed.

**2026-08-09**

- **A one-off data-fix script must import the same code the application runs, or it writes the fields and skips the derived ones.** A correction script set `sys.path` to the main checkout while the new columns lived on a worktree branch, so its `update_person` predated them: 13 corrections landed and every derived value went stale. `doctor` caught it, which is the only reason it was noticed. Point the script at the code under test, and re-run the invariant check afterwards — a data fix is a write path like any other.
- **When the primary source 403s, cite the aggregator you could actually fetch — and put the caveat in the record, not just in the chat.** A research pass hit 403s on three primary-source domains, leaving only search-engine snippets to reconstruct the facts. The durable move was to cite a fetchable trade-press aggregator (and it covered the same announcement) as the record's source rather than the blocked primary URL, and to write `Caveat: could not directly fetch <host> (403) — only WebSearch snippets confirm this` **into the row itself**. A citation you could not read is a citation you cannot defend later; a snippet-derived date belongs marked as unconfirmed (`~2026-02-25/26`) rather than stated flat. The caveat has to live in the dataset because the session that knew about it will be gone.

**2026-08-23**

- **Hand-curated catalog rows can be stale the day they're written — treat curation as claims needing a verification pass, not facts needing a future audit.** A coal-plant catalog written in August carried "Cumberland retires 2028"; the owner's board had reversed that retirement *six months earlier*, and the sweep that wrote the row had verified the marquee rows but back-filled the rest from general knowledge. Quarterly re-audit cadences don't fix this — the row was born dead. What does: (1) per-row `source_url` + `verified_at` so unverified rows are *visibly* unverified, (2) a domain-expert verification pass over every row BEFORE first ship (the second agent's 24 primary-source checks caught it), (3) enforcement in the data validator so a citation-less curated row fails CI. Curated ≠ exempt from the provenance discipline applied to scraped data — curated rows need it *more*, because nothing upstream refreshes them.
- **A 200-with-bytes fetch can still be a non-capture: JS-shell sites (some hosts) return a nav-only stub to urllib that looks like a successful cache.** After caching any page, grep the cached bytes for the fact you came for before citing it; the failure is silent twice — the fetch "succeeds" and the index row looks healthy. Upgrade to the 2026-08-09 403 rule: before settling for an aggregator, the browser pane can usually capture the blocked primary itself (see AGENTS.md browser-scrape section for the flow, incl. chunked PDF fetch); cite the primary once its bytes are actually in the cache.
- **Never cite a fact that exists only in a search-result summary.** Summaries synthesize across sources; the page is the source. One summary supplied a precise date ("May 30, 2025") that its cited page never contained — the page carried only the event, not that date.

**2026-08-24**

- **Frame a map view on the feature that defines the question, never on the union of everything returned.** A per-site environmental screen (a per-site screening tool, a site-screening data app) legitimately returns multi-state CONTEXT polygons alongside the subject — USACE regulatory districts, wetland delineation regions — so `layer.getBounds()` over the combined FeatureCollection zoomed a 5-mile screen out to zoom 4, half the country, while the success toast fired normally. Context geometry ≠ subject geometry: fit to the semantic region-of-interest feature (the ROI buffer / project location), and fall back to the union only when no ROI feature exists. Generalizes to any "show my results on a map" flow, and the failure is invisible in code review — it only fell out of a headless test asserting `zoom >= 8` after the click.

**2026-08-30**

- **A projected area or length is not a ground measurement, and the service labelling its units correctly is what makes it dangerous.** A state GIS service's building footprints publish `Shape__Area` with `geometryProperties.units: "esriMeters"` — true, and still not square metres of roof: the layer's spatial reference is Web Mercator (EPSG:3857), where area is inflated by sec² of the latitude, about **1.61×** at the state's 38° N latitude. A caller reading the number as ground area overstates every building by more than half, and nothing in the response says so. Check the layer's `spatialReference` before believing any `Shape__Area`/`Shape__Length`, and either convert (dividing by sec²(lat), declaring the conversion and the latitude it used) or return the raw value under a field name that carries the projection — `footprint_area_web_mercator_sq_m`, not `area`. Same disease as a units-free number, one layer up: the units are right and the datum is wrong.
- **The service with the authoritative-sounding name is often the republished one — read the field names for provenance before the title.** A state DOT publishes both a `Primary_and_Secondary_Roads` layer and an `LRS_Route_Master` layer. The first sounds like the operating agency's road network and is a Census TIGER extract: its fields are `LINEARID`, `MTFCC`, `RTTYP`, `FULLNAME` (all TIGER's), and it holds 9,344 features for the whole state. The second, whose name suggests an internal system, is the DOT's own inventory — 196,896 routes with official state measures and an annual release date in its own service description. Registering the first as "the agency's own data" would have been an authority error that nothing downstream could detect. Field names are a provenance fingerprint: `GEOID`/`MTFCC`/`LINEARID` mean Census, `HUC` means a federal watershed model, and a distinctive agency-specific prefix means the agency's own schema.
- **A ticket's or spec's description of a field is a hypothesis; the live schema is the fact.** An issue specifying a source stated `PLACENAME` was the postal place and instructed mapping it as such — the exact trap the tool was meant to warn about. Read live, `PLACENAME` holds facility names ("Rose Hill Elementary School", "ABC Store 099") and is empty for ordinary residential addresses; the postal city is a different column, `PO_NAME`. Mapping it as written would have put a school's name where a city belonged, in the field a downstream warning told callers to distrust. Sample real rows for every field you map, including the ones the ticket author says they verified, and pin the mapping with a test naming what the field actually holds.
