## Testing & validation

- **Write tests alongside code.** Every new module or bug fix includes them.
- **Regression-test every bug fix.** The bug is the test case; without one the fix rots.
- **Test the seam where a check is *wired in*, not just the checking function.** A unit test of the pure predicate passes happily while the predicate sits disconnected — a curation gate's 16 assertions all stayed green after deleting the single line that called it, and the validator exited 0 on exactly the bad data the gate existed to reject. The test proved the helper worked; nothing proved anything *used* it. Assert the observable outcome (`validate(badData).ok === false`), not the helper's return value, and export a seam that includes the wiring if you need one. **Prove it by sabotage:** unhook the check, confirm the suite goes red, put it back. A regression test you haven't watched fail is a guess. **And assert the sabotage actually landed** — the mutation is code too, and it can silently no-op. A guard reported SILENT on the one mutation whose `replace()` matched nothing (the setup had already removed the string it was looking for), so the "failing" guard was fine and the *test of the test* was broken; another minute and a working guard would have been "fixed." Any sabotage that edits a file should assert the file changed (`assert marker in before and marker not in after`) before you believe red or green. A no-op mutation reads exactly like a vacuous guard.
- **Lock every displayed quote and citation to its evidence with a test.** Assert each quoted phrase appears *verbatim* in a stored evidence snippet, and that each citation link resolves to the exact location carrying the quote (when a precise locator is missing, e.g. some regulatory PDFs drop paragraph numbers from the text layer, anchor to the verifiable physical page instead). A future edit to a quote, or a reworded source, then fails loudly until re-verified, instead of silently drifting. This closes the gap a schema check can't see: well-formed text that no longer matches its source.
- **Don't claim text is "identical across all N" without checking every instance.** Template clauses, boilerplate, and multi-order statements look alike but differ subtly. A claim of "identical across all N" is provably false the moment one variant exists. Safe wording: "largely common, with per-instance tailoring." Safe test: check each quote against its own cited document — not just the canonical copy.
- **Stamp a page number on every quote surfaced from a multi-page document.** Locate the quote's start in the page-marked body text (`--- PAGE N ---`) and store the page it begins on. Render as `p. N` after the quote, linked to the filing. Guard with a test that recomputes every stored page so a stale or hand-edited number fails loudly; `null` when the start can't be located, never a guess.
- **A test that re-implements the logic tests your model, not the machine — and the bug lives in the gap.** A privacy feature (render a page with every personal field stripped) was guarded by a Python test mirroring the JS transform, reading the same rule file so only the traversal was written twice. It passed. The live page still leaked 16 hits of the owner's name, because the test validated the *transform* while the bug was in the *render lifecycle*: switching to the stripped view left the previous view's DOM nodes in place. **A fresh load was clean and only a transition was dirty**, which is exactly the state a data-level test cannot see. If a transform's output is consumed by something stateful, assert on the consumer's real output (read the built artifact / the live DOM), and *first* confirm the same assertion fires on the un-transformed case — a leak check that finds nothing everywhere is broken, not passing. Corollary: some records *legitimately* give one guard nothing to find (a roles-0 record has no role-title patterns to leak); don't force that guard to fire, which would mean fabricating data, prove the projection is non-vacuous through a companion guard that *does* fire (the personal-name patterns) and exempt the empty guard for that case explicitly.
- **Hiding is not removing, and the branch you don't render is where stale state survives.** The above bug was one early `return` after setting `hidden` on a section, so the container was never cleared: eight cards and their links sat invisible in the DOM of a page whose entire promise was that they were gone. Whenever a view conditionally renders a region, clear the region it *doesn't* render, structurally — mark every write target (`data-render`) and empty them all before each render, rather than remembering per-branch. Then guard the marking itself (grep the render code for write targets, fail if one is untagged), because the next section someone adds is the one they forget.
- **Validate output against schemas before writing to disk** (Pydantic `extra="forbid"`, or zod).
- **A local `conftest.py` fixture silently SHADOWS a plugin fixture of the same name.** `pytest-playwright` publishes `page` / `browser` / `context`; a project conftest defining `page` wins invisibly — a reader can't tell which one a test receives, and deleting the local one hands every test a differently-configured object instead of failing. Name project fixtures distinctly (`site_page`, `site_browser`), and run `pytest --fixtures` whenever adding a fixture with a common name.
- **A browser/e2e suite should skip itself, not fail, when its dependency is absent.** Guard collection (`collect_ignore_glob` on `ImportError`, plus checks that the browser binary and any built fixtures exist), pin the driver in a separate `requirements-dev.txt`, and leave the runtime `requirements.txt` untouched. Then `pytest` stays one command on a bare checkout. Verify *both* paths before claiming it: run the suite with the dep, and again with the import blocked — the skip path is exactly the one that rots unnoticed.
- **Validate external/LLM output only as strictly as the app actually consumes it.** A required-string schema on a field the rest of the stack already treats as optional (nullable column, UI fallback) turns a cosmetic model quirk into a hard user-facing failure — an LLM returning `emoji: null` 502'd a whole generation against `z.string()`, even though that field was nullable in the DB and had a `?? "⭐"` UI fallback. Loosen optional/cosmetic fields (`nullable`/`nullish` + transform-to-default); keep only load-bearing fields (the ones that drive real behavior) strict. Regression-test the null/missing case, because the model returns it reliably, not rarely.
- **Cover edges:** empty `[] / {} / ""`, null for every optional field, boundary values, combined filters.
- **Count-floor regression test.** For append-only datasets, assert total/item counts never drop versus the previous commit. Reintroduced caps and accidental deletions pass schema validation but fail a count floor.
- **Guard the whole garbage class, not the one bad row.** When a loose parser emits junk (a Table-of-Contents dotted-leader line harvested as a "finding"), don't just delete that row. Add a guard that scans committed output for the failure *signature*: dotted/ellipsis TOC leaders (`\.{6,}`, `…{2,}`), glyph artifacts (`(cid:NN)`), runaway field length, contentless titles. The signature catches the next variant before it ships. The cause is usually an unbounded greedy match (a final field that swallowed the rest of the document); bound the parse region and cap field length at the source.
- **A whole-word guard that greps entity names false-positives on a name that is also a language token.** A cross-bundle guard grepping every other company's name as `\bNAME\b` case-insensitively across every emitted byte broke the instant a company was named "SPAN". The engine files legitimately contain `<span>`, `el("span")`, and a `.proof span` selector, so registering SPAN would have failed the build for every *other* company at once (an all-bundles failure, caught by one `grep` at planning time, not after). Before adding an entity name to any name-matching guard, `grep` the codebase for the bare word; if it collides with markup, keywords, or identifiers, narrow *that name's* check to author-controlled content (keep full-byte coverage for distinctive names) and regression-test that no other record uses the bare word. Same disease as hardcoding an allowlist without surveying the real distribution, applied to a guard's own matching.
- **Seed one example per enum value.** When the UI renders a legend/chips off an enum, test the dataset ships ≥ 1 record per value, so no legend slot renders empty and deleting the last example fails loudly.
- **Mock a real recorded response, not a synthesized shape.** A mocked unit test can pass against a shape the live API never actually returns, hiding contract drift indefinitely. Validate at least one mock against a real recorded response.
- **A verbatim-quote/citation test must sweep every field capable of carrying a quote, not just the primary one.** A coverage gap in the guard itself (one field the test forgot to scan) lets fabricated or unverified content ship silently through the exact defense meant to catch it.
- **Renaming or expanding an enum's values needs a repo-wide grep for the literal old strings, not just fixing what the type-checker flags.** Hardcoded copies in test mocks, seed JSON, and frontend constant maps drift silently; only the type-safe call sites get caught by the compiler. Concrete case: a CSS file's `.badge-reason-<value>` classes lagged a Python enum rename — the two orphaned old-name rules and one missing new value weren't caught by any test (CSS class names aren't type-checked), and the affected UI elements silently rendered with no color and no spacing rather than erroring.
- **Same disease, different host: deleting an HTML element/attribute that a project's own automation script writes into is a content edit with a code consequence.** A cosmetic ask ("remove this footer line") deleted a `<span data-site-updated>`, leaving an unrelated refresh script's regex pointed at nothing — every future run of that script would have silently printed a "stamp not found" warning on stderr forever, instead of failing loudly or getting fixed. The surface that looks complete (the page renders fine, the diff is one line) isn't the surface that actually consumes the thing you deleted. `grep -rn` the attribute/class/selector across `tools/`/`scripts/` before calling any markup deletion done.
- **A redundant ternary (`x if cond else x`, both branches identical) is a distinct bug class worth its own review check.** It silently breaks direction/role-assignment logic while reading as correct on a skim, since the branches look intentional.
- **When a parser walks markers/sections to bound a range (start-of-zone, end-of-zone), add a self-check that an independently-computed count matches the walk.** `str.find()` only locates the *first* occurrence per page/doc; a marker that repeats (2–4 agencies packed on one page) silently merges into one blob. Count matches with a raw regex `findall` over the same text and `assert` it equals what the walk visited, raising on mismatch — this catches the coverage bug automatically instead of needing a manual audit to notice content merged that shouldn't have.
- **A review scoped in advance to "the files I expect matter" has a blind spot exactly where you didn't look.** Filtering a self-review to `scripts/`+`tests/`+docs missed a hardcoded citation-label map in `app.js` that broke in production (rendered `"undefined · p. N"`); an automated full-diff review caught it. Run (or accept) a full-diff pass in addition to any targeted review — the bugs worth finding are often outside the range you predicted.
- **Every commit gets an adversarial code review before merge, even code the same session wrote and tested.** A session-authored, session-tested feature that passed its own live validation still had reproducible crash bugs and a range-handling bug that silently understated real figures by orders of magnitude, none caught by its own unit tests. One bug was only found by re-running the real pipeline on real data and reading the diff after an earlier fix, not by the passing tests. A fix passing its own tests is necessary, not sufficient: run it against real data and inspect the output before trusting it.
- **A timing/ordering race won't reproduce on a fast local harness — force the order, or the test passes without the fix.** A parallel-load bug (a small enrichment file resolving before a 10× larger data file, so a join dropped 92% of its records) had a first regression test that PASSED against the buggy code, because a local `http.server` served the big file fast enough to win the race every run. The test only became a real guard once it *forced* the losing order — delay the file that must arrive first (Playwright `page.route` + sleep, a fault-injection hook, a fake clock). Rule: for any race, prove the test FAILS on the unfixed code before trusting it; if you can't make it fail, it isn't testing the race.
- **Keep the tool that FOUND the defect, not only the one that now prevents it.** A corpus passed every
  check it had, so the defects were found by a throwaway script that printed *distributions* — link
  asymmetry, empty containers, vocabulary spread, name reuse. Three of its findings became hard
  assertions and the script was deleted. That is backwards: the assertions enforce the failure modes
  already known, and the survey is how the *next* unknown one becomes visible. Keep both, and keep them
  distinct — the validator is a gate that fails the build, the survey prints and exits 0, with a
  "should be zero" set at the top and distributions below it that are deliberately *not* asserted. When
  a distribution turns out to be a real defect, promote it into the gate and leave the line in the
  survey so the number stays visible.
- **A manual check you have run more than twice is a missing test.** Chronological ordering of a
  rendered list was verified with an ad-hoc one-liner four times in one session, and hand-fixed four
  times, because nothing asserted it. The tell is re-typing the same throwaway command; that is the
  spec for the test you have not written yet. Watch for the legitimate exception when you write it —
  here, span entries whose sort key is a placement hint rather than a real timestamp had to be exempted
  explicitly, which is a fact about the data worth recording in the test's comment.

- **A test that extracts its subject from a source file can pass *vacuously* — make the extractor fail loudly, then mutation-check the assertions.** When a test slices its data out of something else (JS literals out of an HTML page, a block out of a config, a table out of a README), the extractor is a silent single point of failure: if a marker moves and the slice comes back empty, a `for (const x of extracted)` loop iterates zero times and every assertion "passes" forever. Two guards, both cheap: (1) treat "found nothing to check" as a failure, not a skip — assert the extraction located its markers and returned a non-empty subject; (2) before trusting the suite, break the invariant on purpose (duplicate an id, typo a key, reorder a sequence) and confirm each assertion class actually fires with the exit code you expect, then restore. Generalizes the race rule below: *any* new assertion should be proven capable of failing, not just timing ones — a green test you have never seen go red is a hypothesis, not a guard.
- **Closing a "done but unchecked" backlog item means verifying the fix is live AND adding the regression test it shipped without.** Several fixes had landed in prior sessions but were never guarded; the backlog still listed them as open. Don't just tick the box — confirm the current code actually contains the fix (grep the symbol/behavior), then add the missing test so it can't silently regress. A fix with no test is a re-open waiting to happen.
- **A new writer's output path must not collide with a file it also reads.** A connector whose `docs/data/<slug>.json` output slug matched the overlay filename it consumed silently clobbered that overlay on first run. When a component both reads and writes under a shared naming scheme, assert the two paths differ (a test on the constant), not just at review time.
- **Measuring a JS-rendered page to verify a change? Sample after render settles, not at a fixed short delay — an async page under-reports.** A page's mobile scroll height read 2.9 screens before its fetch-and-render tables populated, then 23.7 after they did. A decision made off the early number (which page is "too long", whether a layout fix worked) targets the wrong thing. Poll until the metric is stable across two reads, wait on a render-complete signal, or at minimum re-measure once more before trusting it.
- **Hiding content behind a disclosure, tab, or accordion breaks every test that waits on it — and the fix is to drive the UI, not to loosen the wait.** Children of a closed `<details>` or an inactive tab panel are *attached but not painted*, so a default `state="visible"` wait times out and `inner_text()` returns `""` while `text_content()` still works. Two IA changes in one session broke 4 and 28 tests respectively this way. Prefer clicking the disclosure (what a reader does) over switching to `state="attached"`; reserve `attached` for tests that are about DOM contents rather than what's on screen. Corollary: **changing which view/tab is default breaks every test that lands on the root and waits on another view's DOM** — route those through the deep link instead.
- **Driving an SPA with `page.goto(base + "#hash")` does not reload the document, so hash-routed navigation never fires.** Successive `goto`s that differ only in the fragment are same-document navigations; a screenshot harness written this way silently captured four un-rendered tabs and reported "wait failed" rather than anything actionable. Add a cache-busting query (`/?i=<name>#hash`) or call `reload()` when each case needs a cold load.
- **Never assert a layout measurement against an exact pixel floor — device scaling makes it sub-pixel.** A `min-height: 44px` control measures `43.999969...` via `getBoundingClientRect` in a device-scaled mobile context, so a bare `height < 44` check fails roughly one run in five against perfectly correct CSS. It reads as flake and gets "fixed" by re-running. Compare against a half-pixel tolerance (`>= FLOOR - 0.5`) and name the constant. Confirm the tolerance still catches the real regression by mutating the rule away — 39px must still fail.
- **A guard for a *directional* bug usually inherits the bug's direction — mutate the fix away or you have written the bug twice.** A navigation helper walked *ancestors* to open collapsed sections, and so missed a target whose collapsed element was a *child*. The test written to guard every such target used `el.closest(...)` — which also only looks upward — so reverting the fix left the new test green. Whenever a bug has an axis (up/down, inner/outer, before/after, left/right), the obvious API for checking it tends to share that axis. Check both directions explicitly, and confirm the assertion goes red with the fix removed.
- **Two tests that look like one guard can each cover a different half, and neither cover the whole.** A roving-`tabindex` pair: the "static markup is correct" test passes from the authored HTML alone and stays green when the JS that maintains it is deleted; only the "selection moves the tab stop" test catches that. Mutation-check each assertion separately and say in the docstring which half it owns — otherwise a later reader deletes the "redundant" one and silently loses the only real coverage.
- **"Does this name appear anywhere in the source?" is not a usage check.** A dead-CSS guard that substring-matched class names against the markup passed for three orphaned `.rp-commitments` rules, because an **id** of the same name existed on an element whose class was something else. Ids, comments, data attributes, and unrelated strings all answer yes. Parse the actual application sites (`class="..."`, `className =`, `classList.add(...)`, your framework's element helper) — the rewrite found two more dead selectors immediately. And when you tighten a check this way, **run it against known-good code first**: the strict version reported two live classes as dead, because `class="btn${active ? " on" : ""}"` makes the attribute regex stop at the quote *inside* the interpolation, leaving a truncated token that matches nothing. A guard that cries wolf gets disabled.
- **Settle "is this valid HTML?" with a validator, not from memory — one curl answers it and finds everything else at the same time.** A review claimed two things about `<summary>`'s content model; the W3C Nu validator (`curl -H "Content-Type: text/html" --data-binary @page.html "https://validator.w3.org/nu/?out=json"`) confirmed one and refuted the other, because the spec had changed to "phrasing content, optionally intermixed with heading content" in a way that's easy to misremember in either direction. The same single call surfaced **22 pre-existing errors** nobody had gone looking for — including four `aria-label`s on bare `<div>`s, which AT silently ignores, so four regions were unlabelled for screen-reader users while looking correct in every screenshot. Run it once per project and wire it into CI so the count can only go down.
- **Run the full suite before committing.**
- **Never ship test files to production.** CI excludes tests, fixtures, debug artifacts.
- **Tests are the eval suite**, the loop that tells you what works. Invest in it.

---

- **A cross-check between a parse and its source passes vacuously when both sides are zero.** A guard comparing "rows parsed" to "rows listed in the file" looked airtight, and it was — until the class name itself was renamed, at which point the parser found 0 and the counter found 0, `0 == 0` agreed, and an empty generated file sailed through the exact check written to stop it. This is the total-failure case, i.e. the one that matters most. Every consistency assertion needs an **independent non-zero floor** next to it (`if not listed: fail`), plus a check that the parsed rows aren't hollow (a renamed inner span yielded real-looking entries with empty names, which the count check also waved through). Found only by mutating the input four ways and asserting a non-zero exit each time — reading the guard made it look correct.

- **A compression pass can leave a dangling cross-reference while every individual sentence still reads perfectly.** Cutting a case study's bullets to a word budget removed the sentence explaining what "Item E-2" was, but left the heading that referenced it — so a reader met the term and never learned it. Re-reading the edited text will not catch this, because the new text is fine *on its own*; the break is between what survived and what didn't. Diff the **figures and proper nouns** across the before/after versions (`set(before) - set(after)`) and check each casualty is redundant. Found this only by diffing numeric tokens between an old branch and HEAD, which is a cheap check worth running after any large editorial pass.

**2026-08-05**

- **A review finding is a sample, not a bug report — grep for the pattern before calling it fixed.** Across thirteen bot-review rounds on one PR, **five of the nine real findings were reported as a single row and were actually a class**. One "this source doesn't support its claim" became five roster bases citing sources that established half of what they said. One "this article is mislabelled as government-reported" became **34 of 60 records** once the label was derived from the source host instead of read by eye. One "this band's entrant count is wrong" was the same zero-versus-unknown conflation already fixed elsewhere in the session and missed here because the earlier fix was applied where the defect was *reported* rather than everywhere the pattern occurred. Fix the row, then run the query that finds its siblings; the count you get back is usually the finding.

- **Three shapes of guard that can never fail, all found by mutation in one session.** (1) `assert.ok(css.indexOf(a) < css.indexOf(b))` **passes when `a` is deleted**, because `indexOf` returns `-1` and `-1` is less than any real index — assert both operands are `>= 0` first. (2) An assertion comparing rendered output against *the same function the renderer calls* is self-consistent by construction; assert on literal expected text instead. (3) An "empty state is present" check that greps the whole page matches a **different** lane's copy, so deleting the lane under test stays green — count occurrences and assert both directions (present when empty, absent when populated). Each looked airtight on the page and each survived the defect it was written for.

- **A guard written for a reported defect usually covers the instance, not the class.** In one round, four separate mutations all stayed green against existing guards: the lane check only inspected the two lanes where the bug was first reported, and the capital check only looked for the word "debt". Widen the guard to the rule ("no licensing verb in any physical-lane label", "every equity amount states a dollar figure") rather than to the example. Then re-run every earlier mutation, because widening one guard sometimes lets another regress.

- **A numeric CLI argument that reaches `Number()` unvalidated turns "check everything" into "check nothing" and exits 0.** `--limit notanumber` produced `NaN`, `slice(0, NaN)` returned `[]`, and the link checker printed `live 0 · blocked 0 · dead 0` and exited **success**. A typo in a CI step or an empty shell variable would have made a validation job pass while validating nothing. Validate the parse (`Number.isInteger(n) && n > 0`) and treat an empty work list as a failure, not a skip.

- **A test that reads a generated file cannot see a change to its generator.** A guard asserting the committed `llms.txt` said "1 company" rather than "1 companies" passed happily after the pluralisation fix was reverted in the *generator*, because the file on disk was still the corrected one. The test was checking an artifact, not the code that produces it. Any generated-artifact guard needs to **run the generator** (`node build-x.mjs --check`, which regenerates and byte-compares) rather than read its output; otherwise it verifies a snapshot nobody can regress. Caught only by mutating the generator and watching the suite stay green.

- **The code that shipped with zero review rounds is where the bugs are, and it is worth reviewing on that basis alone.** Ten of fourteen findings in one post-merge review sat in four small scripts written in the final turn before merging, while the heavily-reviewed application code that had been through thirteen bot rounds produced two. Recency of scrutiny predicts defect density better than complexity does. When a change lands late in a session, review it *because* it landed late.

- **Predicting a validator's output by re-deriving its logic from memory, instead of running it or copying its exact computation, is a silent overcount/undercount waiting to happen.** A quick ad-hoc script meant to preview a coverage metric before the real check ran included one extra data field the real validator deliberately excludes; the guess came back 7x higher than the real script's answer for the identical input. The fix isn't "double-check the guess" — it's to never guess: copy the real computation verbatim (or just run the real tool) whenever you need its number before committing to a value that depends on it.

- **A property the data must satisfy mathematically is the cheapest validator you will ever write, and the only one that proves rather than suggests.** A dataset of 46,759 sites carried six "distance to nearest X" fields with no way to check them short of re-querying every source. But nearest-feature distance is 1-Lipschitz in position: for any two sites, `|d(A) − d(B)| ≤ dist(A, B)`. Both operands are already on disk, so a violation is a *proof* of a defect needing no external source — and it swept 511,927 near-pairs in seconds. Before building an expensive ground-truth harness, ask what the data must be true of on its own terms: monotonicity, triangle inequality, conservation, idempotence, a sum that must equal its parts.

- **Fuzz the algorithm against brute force before suspecting the data.** Faced with distance values that looked impossible, the obvious suspect was the pure-Python spatial index (grid bucketing plus a Chebyshev ring-expansion early exit — exactly the kind of bound that is easy to get subtly wrong in degrees-vs-metres). Eleven randomised tests comparing it to an exhaustive scan across four latitude bands settled it in minutes: the index was exact, so the fault had to be upstream. It was — in the checking harness. A cheap correctness proof on the component you doubt redirects the whole investigation.

- **When comparing two results from the same numeric routine, measure with that routine's own constants.** The Lipschitz property above "failed" by 2×10⁻⁴ mi until the test stopped using 69 mi/degree and started using the index's own 110,540 m/degree. A different earth model in the assertion manufactures failures at exactly the scale a real bug would hide in. Then allow for genuine drift: each query projected at its own latitude, so the property holds only to ~0.01%, and the tolerance has to say so.

- **Prove the guard fails.** A new assertion that has never been seen red is a hypothesis. After adding a check that research PDFs never enter the published directory, copying one in and watching it fail took ten seconds and was the only evidence the guard worked at all. Same for a leaked-secret scanner, a size budget, a schema gate: break it once, on purpose, before trusting it.

- **`pgrep -f "<project path>"` will not find the stray that is breaking you.** A leaked `python3 -m http.server 8765` from an e2e run shadowed the real dev server on the same port — the more specific `127.0.0.1` bind wins — so the preview served a bare directory listing and `/index.html` 404'd while the app had loaded fine moments earlier. The orphan sweep missed it because its command line contains no project path. Add `lsof -nP -iTCP:<port> -sTCP:LISTEN` to the sweep, and when a served file that exists starts 404ing, ask *who is answering* (`curl -sI` — the `Server:` header names the culprit) before debugging the app.

**2026-08-09**

- **Two test processes running at once produce phantom failures that look exactly like regressions.** A backgrounded `pytest` outlived its turn and competed with a new run; the second reported timeouts and setup ERRORs on browser tests that pass alone in 6 seconds, and the whole suite hung past ten minutes. Before diagnosing any timeout, `pgrep -fl pytest` (and kill strays). Same family as the stray-server rule above: ask *who else is running* before believing the failure.
- **Isolate a suspected regression by running one probe against `HEAD` and against the working tree, then bisect by file.** Rather than reasoning about which edit broke a render, `git stash push -- web/` → probe → `stash pop` answered it in two runs (`HEAD` 29 rows, working tree 0), and a second pass over `web/app.js` alone versus `web/styles.css` alone named the file. Faster and more certain than reading a diff, and it works when nothing throws.
- **A fixture that cannot distinguish the right answer from the wrong one proves nothing — check its size against the threshold it exercises.** A truncation test used a 137-character block against a 140-character limit, so it passed whether or not truncation existed. The tell is a fixture whose measurement sits near the boundary; assert the boundary is actually crossed.

**2026-08-10**

- **A test parametrized across one axis (viewport width, locale, theme) but pinned to the default on another (route, tab, filter) only covers the pinned value.** `test_no_horizontal_page_scroll` ran at 3 widths, every run via a page-load helper whose default arg always opened the first/default tab — whose content happened to be short. The other 4 of 5 tabs each had a real horizontal-overflow bug (one bad enough to render a table 1650px wide at a 1280px viewport) that this test could never have caught, because the pinned axis was exactly where the bug lived. Widening the SAME test to also parametrize the pinned axis (not writing a new test) found it in one pass. When a test's helper takes an optional parameter with a default, ask what class of bug only appears when that parameter is something other than the default — that's the coverage this test doesn't have.

**2026-08-10**

- **A canary asserting one hardcoded literal breaks on the rename it was never about.** A prose linter's "did the extractor find anything?" guard asserted the string `"Reconnect"` was extractable; absorbing that view into another one turned the guard red, correctly but uselessly — nothing was wrong with the extractor. Swapping in a *different* hardcoded word just moves the trap one rename along. Derive the canary from the thing under test instead: count `text: "…"` literals in the source with a cruder regex than the extractor's own and assert the extractor returns at least that many. That cannot rot on a rename and still fires the instant a marker moves and the extraction silently empties.
- **When a phase retires the surface a test was pinning, widen the test into the invariant it was protecting — do not delete it with the surface.** A test asserted the People table scrolls sideways inside its wrapper at 375px. That was correct while People *was* the squeezed desktop table, and after the redesign it pinned exactly what had just been removed. Deleting it would have dropped real coverage; keeping it would have blocked the change. It became "across every view, nothing may push the page sideways, and anything wider than the viewport carries its own overflow" — same intent, five views instead of one, and it survives the next redesign too.
- **A vacuity check names a specific element, so it has to be re-pointed when that element changes shape.** `test_the_touch_floor_check_is_not_vacuous` measured a nav item in a fine-pointer context and asserted it was *under* 44px, proving the coarse-pointer media query was doing real work. A new bottom bar made nav items fill the bar's height at every pointer type, so the check would have passed with the 44px rule deleted — the guard's guard had gone hollow. Whenever a component gains an intrinsic size, grep for the tests that assert it is *small*.
- **Headless Chromium does not always advance a CSS entrance animation, so "the box stopped moving" is not "the layout settled".** A bottom sheet slides up 12px over 140ms. Two identical mid-slide reads 30ms apart looked settled to a pixel-polling helper, and the test measured the animation's *first frame* against a layout that is provably correct in a real browser — a 12px false failure. Ask the platform instead of inferring from pixels: `await Promise.all([...el.getAnimations()].map(a => a.finished))`, then poll. Pixel polling alone answers a different question than the one you asked.
- **A mutation harness that reports GREEN deserves one hand re-check before you conclude a guard is vacuous.** A batch script sabotaged two fixes in one file back to back and reported the second guard GREEN; run in isolation immediately afterwards it was correctly RED, and it stayed RED across four further scripted attempts with and without clearing `__pycache__`. The script had asserted the sabotage landed on disk, and it had. Unreproducible, cause unknown — but the cost of believing a false GREEN is deleting a working test, so spend the thirty seconds.
- **A count captured when a module-scoped fixture was seeded is stale by the time later tests read it.** A test compared a rendered card count against `live_server["total"]`, recorded at seed time; an earlier test in the same module creates a person through the API. It passed alone and failed in the full run. Compare the two things you actually mean to compare — here, the wall against the list *in the same page* — rather than either against a number frozen earlier. Same family as the shared-fixture-queue trap, with a number instead of a queue.
- **A guard that scans the working tree fails on files you have not committed, which is a feature worth expecting.** A "no machine-local paths" hygiene test went red on an uncommitted launch config and again on a resume document written minutes later. Both were real (`/Users/<name>/…` would have shipped), but the failure arrives while you are mid-thought about something else. Expect it, and prefer repo-relative paths in scratch files too.
- **A test that substring-searches a block of source for a banned/allowed term can be tripped by a comment that merely names the term while explaining why it's excluded.** A linter's exclusion list grew a "why" comment ("X was tried and removed, same reasoning as Y") that spelled the excluded word in quotes; a naive `text.includes('"word"')` assertion can't tell that from a real array entry and failed on its own explanatory comment. Parse the actual structured entries (the real `["term", "reason"]` shape, or an AST) and check membership in that parsed set — a raw substring search over a whole block is validating the wrong layer, the same failure shape as a test reading a generated file instead of its generator.
- **A production fallback to the real clock silently defeats an injected `today`, and the test still passes for the wrong reason.** A personal CRM app's date test injected a fixed `today`, but `models.due_date` fell back to `dt.date.today()` — the real clock — for a never-contacted person, so that branch ignored the injection entirely. The suite was green and the diagnosis "stale tests" was wrong: it was a real code bug that only the never-contacted path exposed. When you inject a clock, assert on a date that the **real** clock could not produce (a fixed date years off), so any code path that escapes the injection fails loudly instead of coincidentally agreeing. Grep the module for direct `date.today()`/`datetime.now()` calls after wiring time injection — one missed call site is enough.

**2026-08-23**

- **"Prove the guard fails" applies to shell gates, not just test suites — and `heredoc || echo` is the classic gate that can't fail.** A pre-PR gate's citation-liveness step was written as `python3 - <<'EOF' … EOF || echo "(skipped)"` followed by `[ $? -ne 0 ] && fail=1`: the `|| echo` swallows the python exit, so `$?` tests the *echo* (always 0) and the gate passes with "DEAD CITATION" printed right above "GATE PASSED". Caught only because a review agent seeded the exact defect the step existed to catch. Capture `rc=$?` on the very next line, branch on it explicitly, and before trusting any new shell gate, seed the failure it guards against and watch it actually exit nonzero — the same red-then-green proof demanded of test guards.
- **A test suite that imports a real application module inherits that machine's real `.env` via `load_dotenv()`, including config never meant to reach a test run.** New tests for a Flask app's optional `APP_PASSWORD` gate ("unset → no auth required") all failed as 401 — the developer's own `.env` had a real password set for a same-session LAN test, `load_dotenv()` ran at module import, and the module-level `_APP_PASSWORD = os.environ.get(...)` picked it up before any test could control it. Every "default behavior" test silently needed credentials it never asked for. Fix: an autouse fixture that resets the module-level, env-derived globals a test suite cares about to their documented default, so tests exercise the code's *contract* rather than whatever happens to be in the working directory's `.env` that day; individual tests opt into the non-default via `monkeypatch.setattr`. **2026-08-24**

- **Half-registration is the roster trap: an input registered with a tool's checks but not with its loader fails with a message that misdirects to the data.** A data validator (a site-screening data app's `validate_data.py`) keeps an `OVERLAY_FILES` loader roster AND per-check registries (`OVERLAY_SCHEMA_FILES`, `CURATED_PROVENANCE_FILES`). A new artifact added to both registries but not the loader roster produced `FAIL … missing file or schema class` — which reads like a schema bug and is actually `raw.get(fname)` returning None because the file was never loaded. When a tool separates "what to load" from "what to check," adding a name to one list without the other produces misdirecting failures; grep for every roster the new name must join, and prefer deriving check registries from the loader roster (or asserting registry ⊆ roster) so the drift is impossible.
- **More `pytest-xdist` workers than the machine actually has free capacity for turns a fast suite into a slower AND flakier one.** On a busy dev machine, `-n auto` (8 workers) ran a 105-test Playwright suite in 657s with 21 spurious `TimeoutError` failures; every failing test passed clean when re-run serially or at `-n 4`. Before recommending a higher worker count as a performance fix, measure it against the machine under its ACTUAL current load, not a clean baseline; and before treating any parallel-run failure as a regression, re-run that one test alone or at lower concurrency first.
- **A layout change that alters a page's DEFAULT rendered dimensions (not just adds/removes an element) can break assertions that never mention the thing you changed.** Making a sidebar open-by-default narrowed a map's default width by ~260px on every page load. The fix wasn't a test change; it was noticing that "open by default" is a bigger behavioral change than "nicer shape when open," and that the actual request was satisfiable by the visual/layout change alone. When a UI request is ambiguous between "change the default state" and "change the treatment," the visual-only reading is safer — it's the one least likely to shift dimensions every other test implicitly assumes.

**2026-08-25**

- **A documented flake is a hypothesis, not a diagnosis — and "it passes serially" does not clear it.** The 2026-08-24 xdist rule above says to re-run a parallel-run failure alone before treating it as a regression. Followed literally that is exactly wrong, and it nearly buried a real bug: a DOM-budget guard failed only under `-n 4` and passed every serial run, which matched the documented flake perfectly. It was deterministic — the same number, 5,067, on every parallel run. The serial runs were the *inaccurate* ones. What settles it is not concurrency but an **A/B of the exact failing command against a clean tree**: `git stash` → run the identical invocation → `stash pop`. That took two minutes, proved the failure pre-existed on `origin/main`, and turned "known flake, ignore" into a root cause. Re-running alone tells you the failure is *timing-sensitive*; it never tells you the failure is *wrong*.
- **A readiness signal is only a measurement barrier if it actually gates the thing you measure — otherwise the passing runs are the inaccurate ones.** A first-paint DOM budget waited on the app's own `__APP_READY__` flag, then counted nodes. But the table could still be rebuilt *after* that flag fired, when lazily-loaded records landed and re-sorted it. So the test sampled a moving target: fast machines counted the small pre-rebuild table and passed, loaded machines counted the settled one and failed. The budget was exceeded the whole time; green was the bug. When a test waits for `ready` and then measures, ask what work can still start after `ready` — and prefer waiting on a signal derived from the measured thing itself (row count stable, a rebuild event) over the app's global boot flag.
- **Localize a run-to-run variance by tallying both runs by category and diffing the tallies — the single differing key is the cause, and it is usually one line.** Two runs of the same DOM count differed by 218 nodes, with no obvious culprit across nine views. Instead of reasoning about it, both runs dumped `tag.class → count` for the subtree and the dicts were diffed: exactly one key differed, `span.muted-cell` (255 vs 37), and every other selector matched. That named the fix in one pass — and it *refuted* the two standing hypotheses (pagination over-fire, marker hydration) with hard numbers, since row count and marker count were identical in both. The arithmetic then predicted the outcome before any code changed: `5067−255 = 4849−37 = 4812`, so making that element cost zero nodes had to make both states converge. It did, exactly.
- **An allowlist that suppresses detector hits must match on span *overlap*, not containment — detectors routinely match wider than the phrase you excused.** A writing linter's rule matched `", not a"` (starting at the comma) while the allowlist entry was `"not a determination"`. Containment (`allow.start <= hit.start and hit.end <= allow.end`) was false, so every legal-caveat exemption silently did nothing and the rule fired on exactly the sentences it was written to spare. Caught only because a test asserted a specific exemption worked. Whenever a suppression list and a matcher are written separately, they will disagree about span boundaries; overlap is the forgiving test and the correct one.
- **A guard that greps source text for one spelling of a rule fails the moment the code says it another way.** A test pinned "the fetcher sends no auth headers" by asserting `"headers=" not in inspect.getsource(HttpFetcher)`. A refactor that stored a *response's* headers in a record tripped it instantly — the rule was untouched, only the spelling changed. Walk the AST and check the thing the rule is about: find `Call` nodes whose callee is an outbound method (`get`, `send`, `build_request`, `AsyncClient`) and look for a `headers`/`auth`/`cookies` keyword. A string search over source is a proxy that drifts from the invariant on the first refactor.
- **A threshold calibrated against synthetic data is calibrated against nothing.** A decompression-ratio guard needed a "normal payload passes" test. The first fixture was a JSON body of repeated substrings — it compressed **235x**, far past the 50x limit, so the test would have failed while proving the guard right. The project's five real recorded government responses compress **4.6x to 18.1x**, which is the headroom the limit was actually set against. Drive threshold tests from real recorded payloads, parametrized over all of them, so a future input that breaks the assumption shows up in that test rather than in production.
- **Mock transports do not populate transport-level counters, so a guard keyed on one silently no-ops under test.** `httpx`'s `num_bytes_downloaded` is tracked only by network transports; under `MockTransport` it stays `0` for the whole stream. A decompression-ratio check reading it computed `decoded / 0`, skipped its own guard, and the bomb fixture passed clean. Fall back to a header the mock does carry (`Content-Length`) and state why the fallback is safe — here a server can only *inflate* it, which makes the ratio look smaller, and the absolute byte cap still applies.
